# Testing your agent like a real user (`cinna chat`)

> Read this **when you are about to test the agent by talking to it** with `cinna chat`. It is not about how the agent should behave — it's about how *you* should phrase the test messages.

## Why this matters

When you (a coding agent) test the agent you built, your instinct is to write a **perfect prompt**: every parameter named, every term precise, all context spelled out. Real users never do that. An agent that only works on perfect prompts fails in production on the first hurried, half-typed message.

The point of `cinna chat` testing is to **mimic the real end user** — someone in a hurry, typing on a keyboard (often a phone), who omits context, forgets required details, leans on pronouns, and assumes the agent "just knows."

## The rule: talk like a busy human, not like a spec

Write each test message the way a tired, in-a-hurry person would actually type it:

- **Terse.** A few words, not a paragraph. Lowercase, minimal punctuation.
- **Omit the obvious-to-them.** Leave out context the user assumes the agent already has ("this", "the usual", "again").
- **Forget required details — on purpose.** Drop parameters the agent actually *needs*. This is the most valuable test: does it ask, guess, or break?
- **Use pronouns and back-references.** "send it to her", "same as last time", "the second one".
- **Typos and shorthand are fine.** "tmrw", "pls", "acct", a bare "info@…".
- **One thing at a time, fast.** Real users fire short follow-ups, not one complete brief.

### Example

Optimized agent-style prompt — **do not** test only with this:

> Please send this document for signature to an external signer who does not belong to our company, with name Lex Luthor and email lux@example.com, and the notification message "…".

How a real user actually types it — **test with this**:

> sign this with lux@example.com

The terse version omits the signer's name, the "external signer" flag, and the notification message. A good agent should notice what's missing and **ask** (or apply a sensible, stated default) — not silently invent a name or fail. That gap is exactly what you're probing.

## How to run the test

1. Open with the terse, human message:
   `cinna chat --agent <slug> "sign this with lux@example.com"`
2. **Read the `events` trace, not just the final text.** It shows whether the agent asked for the missing detail, guessed it, or fired a tool with wrong/empty params — that's where realism bugs hide.
3. **Stay in character.** Capture the `session_id` and answer follow-ups just as lazily:
   `cinna chat --resume <id> "lex luthor"` (just the name, nothing else).
4. Try several personas for the same task: the forgetful user, the pronoun-only user ("send it"), the wrong-order user, the typo user.

## What you're looking for

- Does the agent **ask** for missing required info instead of inventing it?
- Does it **resolve references** ("this", "her", "again") correctly — or guess wrong?
- Does it handle incomplete / out-of-order input gracefully?
- Does it fail loudly and helpfully, or silently do the wrong thing?

When a terse message breaks the agent, the fix is usually in the agent's **prompts** (ask-for-missing-info rules, sensible defaults, clarifying questions) — not in making the test message nicer.

## When NOT to use human phrasing

When you're isolating one specific mechanic ("does this tool / credential / endpoint work at all?"), give a complete, precise prompt so a failure points at the mechanic, not at ambiguity. Use human-style messages for **realism / robustness** testing; use precise prompts for **unit-style** capability checks.
