# Git Versioning — guide for the coding agent

> **Read this only when it's relevant:** the agent you're working on is
> git-versioned (a `cinna.agent.json` manifest sits next to `workspace/`, and
> `cinna git status` reports "Linked"), **or** the user asks about git, commits,
> branches, pushing/pulling, or rolling back to a previous version. For ordinary
> build/test work, ignore this file — git versioning is an optional preservation
> layer, not part of the normal edit loop.

## What git versioning is (and what it is not)

A git-versioned agent has **two independent sync layers** on the same folder:

- **Mutagen (runtime, always on).** Keeps `workspace/` mirrored to the running
  container in near-real-time. This is what makes your edits live. Mutagen
  **ignores `.git`** — git and Mutagen never fight over the same folder.
- **Git (preservation, on demand).** Durably versions the same files against the
  agent's **external** git remote — history, snapshots, rollback. You drive it
  with `cinna git …`. Git never touches the container; the two layers meet only
  at the remote.

So: editing a prompt and watching the agent's behavior change = Mutagen. Making a
durable, named snapshot you can return to = git. They are orthogonal — you can
build all day without ever committing.

## Local layout (Model A)

The agent folder you're in (the one holding `.cinna/`) is the repo's
`<subdir>/` node. Its **parent** is the git working tree (the clone root that
holds `.git`):

```
<clone-root>/                 # git working tree (.git lives here)
└── <subdir>/                 # ← this agent folder (== the dir with .cinna/)
    ├── cinna.agent.json      # backend-owned manifest — committed, never hand-edit
    ├── .gitignore            # backend-generated — honor it; never `git add -f`
    ├── workspace/            # the editable agent files (the thing under version control)
    └── .cinna/               # CLI state incl. your token — NEVER committed
```

New checkouts always use this layout, so enabling git later needs no re-download.

## Commands (run from inside this agent folder)

```
cinna git status                    # is it versioned? linked? working-tree status
cinna git link                      # set up the working tree (auto-run by setup when enabled)
cinna git commit -m "msg" [--push]  # stage this agent's subdir + commit (honors .gitignore)
cinna git push                      # push the agent's branch (fast-forward only)
cinna git pull                      # rebase the remote in; Mutagen then updates the live env
cinna git log                       # recent commits touching this agent
cinna git checkout <ref> [--reload] # restore a past version's workspace/ files (see below)
cinna git unlink                    # stop offering git helpers (keeps .git + history)
```

These are **thin wrappers over real git** that run with the developer's own
git/SSH credentials. You can also drop to plain `git -C <clone-root> …` for
anything not wrapped (`git diff`, `git log -p`, `git branch`, …).

## The two-writer, fast-forward-only model — fail loud, never force

Both the backend (its deploy key) and the developer (their own creds) push to the
**same branch**, and both are **fast-forward-only**. When a push is rejected:

1. **Do not force-push.** Never `git push -f` a shared agent branch.
2. Reconcile: `cinna git pull` (rebase), resolve any conflict, then
   `cinna git push` again.

After you push, the **running agent is not updated yet** — the backend is now
behind. Tell the user to click **Pull** on the agent's Git Versioning card in the
web UI (or rely on the configured GitOps webhook). The CLI can't trigger the
backend pull itself.

**Direction guard:** if `cinna git status` shows direction `pull`, local pushes
are rejected by design — that agent is edited on the platform side; pull only.

## Debug / rollback: run a past version without committing

`cinna git checkout <ref>` restores an earlier commit's `workspace/**` into the
working tree as **uncommitted** changes and (with the default `--reload`) flushes
them to the running container via Mutagen. The live agent then runs that version's
prompts and scripts — for debugging or A/B'ing a regression — **without any
commit**. Undo by checking out the current ref again, or `cinna sync pull --force`.

Caveat: `cinna.agent.json` (the DB-owned manifest: SDK config, schedules) is **not**
Mutagen-synced. `--manifest` restores it locally, but reloading it into the agent
still requires the backend (UI "Pull" / webhook). Prompt and script changes — the
common debug case — flow live; manifest-level config does not.

## What is and isn't committed

- **Committed:** `workspace/**` (the agent's source) and `cinna.agent.json`
  (as-is — it's backend-generated; never invent values).
- **Never committed:** `.cinna/` (holds your CLI token!), `workspace/credentials/`,
  `workspace/app-data/`, logs, databases, `__pycache__/`, `*.pyc`, and the
  CLI-generated guides (`CLAUDE.md`, `BUILDING_AGENT.md`, this file, …). The
  committed `.gitignore` plus a local `.git/info/exclude` keep these out — **honor
  them; never `git add -f` a path they exclude.** Before committing, sanity-check
  with `cinna git status` that nothing under `.cinna/` or `credentials/` is staged.

## Enabling git versioning on a not-yet-versioned agent

If `cinna git status` says the agent is *not* git-versioned and the user wants it:
enable **Git Versioning** in the agent's settings on the platform (connect a git
source there), then run `cinna git link`. Because the folder already uses the
Model-A layout, linking needs no re-download or file move — it just initializes
the clone and points it at the remote. A fresh `cinna setup` of an
already-versioned agent links automatically.
