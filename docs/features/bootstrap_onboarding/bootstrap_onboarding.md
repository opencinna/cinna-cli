# Bootstrap & Onboarding (`cinna setup`, `set-token`, `login`, `list`, `status`, `disconnect`, `completion`, `dev`)

## Purpose

The first-contact and lifecycle commands that get a developer from "I have a
setup link" to "my editor is live-synced to a running agent", and keep them
oriented afterwards: authenticate and check out an agent (`setup`), refresh a
stale token in place (`set-token` / `login`), see and inspect what's registered
(`list` / `status`), resume a sync session (`dev` / `redev`), and tear down
cleanly (`disconnect` / `disconnect-all`). `completion` wires the commands into
the shell.

## Mental model — three stores, two token types

A connected agent has its state spread across three places, and onboarding is
mostly about getting them consistent:

- **The agent dir** — the folder holding `.cinna/config.json` (agent id, the CLI
  token, the Mutagen version pin, the git layout) plus the generated guides
  (`CLAUDE.md`, `BUILDING_AGENT.md`, `.mcp.json`, `opencode.json`, `mutagen.yml`)
  and the live `workspace/`. This is what an editor opens.
- **The per-user registry** (`~/.cinna/agents.json`) <!-- nocheck --> — one row per
  agent the user has ever synced: `agent_id → {platform_url, cli_token,
  workspace_path, git?}`. It is the source of truth the sync transport and
  `cinna list` read; the agent dir's config is a per-workspace mirror of the same
  token. Holds live JWTs, so it is `0600`.
- **The platform** — owns the agent, validates every token, and serves the
  one-shot workspace tarball + building context.

Two token types flow through these commands:

- **Setup token** — short-lived (15 min, single-use), generated by the platform
  UI's "Local Development" button and embedded in a `curl | python3` bootstrap.
  Exchanged exactly once for a CLI token; never stored.
- **CLI token** — a JWT with a 7-day rolling expiry (renewed on every successful
  request), revocable from the UI, scoped to one agent. This is what `setup`
  writes and what `set-token` refreshes. The **account token** (refreshed by
  `login`) is its account-workspace sibling — see
  [Account Workspace](../account_workspace/account_workspace.md).

Local vs remote: `setup` downloads the workspace **once** (a tarball) to seed the
folder; from then on **Mutagen** keeps it mirrored to the running container and
the platform is the runtime. `set-token` / `dev` / `list` never re-download — they
only touch tokens, the sync session, and the registry.

## Token exchange — the one server round-trip onboarding depends on

`setup` and `set-token` both funnel through a single helper that `POST`s the
setup token to `/api/cli-setup/{token}` and gets back the agent record + a fresh
CLI token + the platform/frontend URLs. The difference is what they do with it:

- **`setup`** treats the response as a brand-new agent: it decides the on-disk
  layout, refuses if that folder is already a workspace, downloads everything,
  generates the guides, and starts sync.
- **`set-token`** treats it as a refresh: it requires an existing workspace,
  **verifies the exchanged token belongs to the same agent** (aborts if not), and
  rewrites only the stored token in both the config and the registry. No
  re-download, no regenerated guides.

This shared exchange is why a paste of a fresh setup URL fixes an expired token
without re-cloning.

## User flows

### First connection — `cinna setup`
1. In the platform UI, click **Local Development** → copy the `curl … | python3 -`
   command. The developer pastes it into a terminal; the bootstrap script installs
   `cinna-cli` and runs `cinna setup <url>`. (`setup` also accepts the bare URL or
   the raw token directly.)
2. `setup` runs a 5-step flow: exchange the setup token → check/install Mutagen at
   the platform-pinned version → download + extract the workspace tarball →
   generate `BUILDING_AGENT.md` / `CLAUDE.md` / `.mcp.json` / `opencode.json` /
   `.gitignore` → write `mutagen.yml` and start the continuous sync session.
3. The checkout is laid out the **Model-A nested** way (`<slug>/<subdir>/`) so it
   already matches the agent's git repo shape; if the agent is git-versioned the
   CLI auto-runs `git link` here. See
   [Git Versioning](../git_versioning/git_versioning.md).
4. On success the terminal attaches a foreground live-sync session and prints the
   next steps (`cd` in, `cinna dev`, `claude`, `cinna list`, `cinna exec …`).

### Refresh an expired token — `cinna set-token` / `cinna login`
- **Per-agent:** from inside the agent dir, paste a fresh setup token/URL into
  `cinna set-token`. It re-exchanges and swaps the CLI token in `.cinna/config.json`
  and the registry in place. The stored `platform_url` is the fallback when a bare
  token is pasted, so agents on different platforms each refresh from their own dir.
- **Account workspace:** `cinna login` (inside an account workspace) refreshes the
  account token with a browser device-authorization flow — no paste. Run from an
  empty folder it instead bootstraps a *new* account workspace. The paste
  counterpart is `cinna account set-token <token>` (a fresh **account** setup
  token, same in-place swap; this is what Cinna Desktop drives). Full behavior in
  [Account Workspace](../account_workspace/account_workspace.md); after either,
  run `cinna doctor` to re-mint the dependent per-agent tokens (see
  [Doctor](../doctor/doctor.md)).

### See what's connected — `cinna list` / `cinna status`
- `cinna list` reads the per-user registry and prints one row per agent: name +
  id, the web-UI link, the workspace path (flagged **missing** if the folder is
  gone), the live Mutagen sync state, and a **token** probe (`valid` / `expired
  token` / `no connection`) obtained by a cheap authenticated call to
  `/sync-runtime`.
- `cinna status` is the single-agent view from inside a workspace: platform, agent
  id, template, Mutagen version, sync state, pending file counts, conflicts, and
  the same token probe. Run inside an **account** workspace it transparently shows
  the account session instead of erroring.

### Resume a session — `cinna dev` / `cinna redev`
- `cinna dev` starts (or re-creates) the foreground sync session for the agent in
  the current dir and attaches the live TUI. Sync lives exactly as long as the
  process — Ctrl-C stops it, leaving nothing dangling in the shared Mutagen daemon.
  These are everyday **agent-developer** commands (the resume counterpart to the
  sync that `setup` started), not cinna-cli-maintainer-only tooling.
- `cinna redev` is `dev` that auto-resolves the **startup** reconciliation
  conflicts in favor of the remote — for picking an agent back up after it was
  edited on the platform side while the local copy sat idle. Displaced local
  versions are backed up under `.cinna/sync/redev-backup/<timestamp>/` <!-- nocheck -->
  first. Conflicts arising *later* in the session are surfaced normally. See
  [Live Sync](../live_sync/live_sync.md).

### Tear down — `cinna disconnect` / `cinna disconnect-all`
- `cinna disconnect` (inside one agent dir) stops that agent's sync session,
  removes its registry row, and deletes `.cinna/` plus the CLI-generated files —
  but **preserves the user's `workspace/` files**.
- `cinna disconnect-all` (from a parent dir) scans child folders for workspaces
  (handling the nested layout), stops every sync session, removes each registry
  row, and **deletes the directories entirely** — a heavier, destructive cleanup
  behind a typed confirmation. Use `cinna agent unsync` for an account-managed
  child (see [Agent Management](../agent_management/agent_management.md)).

### Driven by another program — no terminal
Cinna Desktop (and CI) run `cinna` as a child process with no TTY. Three
CLI-wide switches make that safe; the account verbs the desktop uses are
described in [Account Workspace](../account_workspace/account_workspace.md).
1. `--no-input` (before or, on the account verbs, after the subcommand; also
   `CINNA_NO_INPUT=1`): every prompt takes its default — machine name, folder
   name, "Continue?" — and a prompt with no default fails with code
   `needs_input`. A confirmation whose default is "No" aborts exactly as if
   Enter had been pressed, so `disconnect` / `disconnect-all` / `redev`-style
   prompts never hang. Mutagen's "run the install command, then press Enter"
   wait becomes a structured `mutagen_missing` / `mutagen_mismatch` error.
2. `--json` (on `account setup` / `set-token` / `status`): one JSON object per
   line on stdout, Rich suppressed, spinners silent; the final line is always
   `{"result": "ok"|"error", …}`. Implies `--no-input`.
3. Stable exit codes, for every command: `0` ok · `10` setup token invalid /
   expired / used · `11` token for another account · `12` platform unreachable
   or 5xx · `1` anything else, carrying a specific machine `code` · `2` usage
   error. Human output is unchanged.
4. `CINNA_MUTAGEN_BIN=<absolute path>` makes every Mutagen invocation (version
   check, session commands, the TUI monitor) use that binary instead of the
   `mutagen` on PATH — the desktop ships its own pinned copy. A path that is not
   executable counts as "not installed", never as a silent fallback.
5. `cinna doctor` and `cinna account status` compare the running cinna-cli with
   the version the platform pins (its `/.well-known/cinna-desktop` discovery
   document) and say `uv tool install cinna-cli==<pin>` when behind; no pin
   means "unknown", not an error.

### Shell completion — `cinna completion`
- `cinna completion --install` auto-detects the shell (or takes `bash|zsh|fish`)
  and appends the activation snippet to the rc file (idempotent — skips if already
  installed). `cinna completion <shell>` prints the raw script for piping; bare
  `cinna completion` prints guidance instead of dumping the script.

## Business rules / guardrails

- **Setup token is single-use and short-lived** — each connection (or refresh)
  needs a fresh one from the UI; the CLI never stores it.
- **`set-token` is agent-bound, fail-loud.** A token for a *different* agent is
  rejected with an instruction to run `setup` in a new directory — it never
  silently rebinds a workspace.
- **`setup` refuses to clobber.** If either the nested target or a legacy flat
  workspace at the clone-root path already holds a `.cinna/config.json`, setup
  aborts and points at `disconnect`.
- **Slug-collision safety.** Two agents whose names normalize to the same folder
  slug don't collide: the second checkout gets an `<slug>-<shorthash>/` clone
  root; re-running setup for the *same* agent reports "already set up".
- **`disconnect` preserves user files; `disconnect-all` deletes directories.** The
  in-dir teardown is non-destructive to `workspace/`; the bulk teardown is
  explicitly destructive and gated by confirmation.
- **The registry is the resolver of record.** A row may outlive its folder
  (`list` flags it **missing**); commands that re-write credentials must not drop
  another concern's state (e.g. a sync re-upsert preserves a linked agent's git
  block) — `cinna doctor` reconciles the drift.
- **Tokens never reach git or world-readable files.** `.cinna/` is gitignored; the
  registry is `0600`.
- **Sync never outlives its process.** `setup` / `dev` / `redev` hold sync in the
  foreground; Ctrl-C terminates the session so the shared Mutagen daemon is left
  clean.
- **Never block without a terminal.** The TTY heuristics (`curl | python3`
  bootstrap, piped spawns) and the explicit `--no-input` flag behave the same:
  defaults or a `needs_input` failure, never a hang. `--json` is a pure
  stdout stream. Exit codes are a contract a driver can switch on.

## Architecture overview

Token + checkout path:

UI setup token → `cinna setup` → `bootstrap.run_setup()` → POST `/api/cli-setup/{token}`
→ CLI token + agent record → write `.cinna/config.json` + `~/.cinna/agents.json` row
→ download `/workspace` tarball → generate guides → `sync_session.start()` → live container.

Refresh path: `cinna set-token` → `bootstrap.run_set_token()` → same exchange → rewrite token only.

Inspect path: `cinna list` / `cinna status` → read `~/.cinna/agents.json` / `.cinna/config.json`
→ probe `/sync-runtime` → render token + sync state.

Teardown path: `cinna disconnect` → `sync_session.stop()` + `remove_agent_registry()`
+ `bootstrap.remove_workspace_artifacts()` → keep `workspace/`.

Error path (every command): body raises `CinnaExit` / `ClickException` / transport error
→ root group normalizes to `CinnaExit(exit_code, code, detail)` → human: `Error: …` on
stderr; `--json`: `{"result": "error", "code", "detail"}` on stdout → process exit code.

## Integration points

- **[Account Workspace](../account_workspace/account_workspace.md)** — `cinna login`
  / `cinna account set-token` refresh the account token; `cinna agent sync` is the
  account-driven alternative to `setup` for checking out agents, `status` falls
  back to the account view, and the desktop-driven `--json` verbs live there.
- **[Agent Management](../agent_management/agent_management.md)** — `cinna agent
  sync` / `unsync` reuse the same provisioning + teardown helpers as `setup` /
  `disconnect`.
- **[Live Sync](../live_sync/live_sync.md)** — `setup` / `dev` / `redev` start and
  attach the Mutagen session; the Mutagen-version pin and TUI live there.
- **[Git Versioning](../git_versioning/git_versioning.md)** — `setup` chooses the
  Model-A layout and auto-links a git-versioned agent on first checkout.
- **[Doctor](../doctor/doctor.md)** — bulk repair of the registry drift that
  `list` surfaces and the token expiry that `set-token` / `login` fix one at a time.
